## Stack

## Request and data flow

```
Request
  └─ server.ts (Oxygen fetch handler)
       ├─ createHydrogenRouterContext()  app/lib/context.ts
       │     ├─ AppSession.init()        app/lib/session.ts  (cookie session)
       │     ├─ getLocaleFromRequest()   app/lib/i18n.ts     (language: cookie → Accept-Language → English)
       │     └─ createHydrogenContext()  → storefront, customerAccount, cart, session, env
       ├─ createRequestHandler()  → React Router
       │     ├─ app/root.tsx loader      header (awaited), footer/cart/isLoggedIn (deferred)
       │     └─ matched route loader/action  app/routes/*.tsx
       ├─ finalizeResponse()      app/lib/response.server.ts (appends the session cookie,
       │                           Vary: Cookie, Accept-Language)
       └─ on 404: storefrontRedirect() (Shopify admin URL redirects)
```

1. **`server.ts`** is the worker entry. It builds the Hydrogen context once per request and
   hands it to React Router through `getLoadContext`. Any thrown error becomes a plain 500.
2. **`app/lib/context.ts`** calls `createHydrogenContext` with the env, a `hydrogen` cache,
   the session, `i18n` and the cart fragment (`CART_QUERY_FRAGMENT` from
   `app/lib/fragments.ts`). It augments `HydrogenCustomCartFragment` so cart calls return the
   codegen'd cart type. `additionalContext` is empty. `SESSION_SECRET` is required.
   The Admin API rating store is created per request from `context.env`
   (`createRatingStore()`), not added to the context.
3. **`app/root.tsx`**
   - `loader`: awaits the `Header` query (shop + `main-menu`). The `Footer` query (`footer`
     menu), `cart.get()` and `customerAccount.isLoggedIn()` are returned as promises
     (streamed). It also returns analytics `shop`/`consent` data, `publicStoreDomain` and
     `locale` (`{code, language, country, tag}`). `Layout` provides it through
     `LocaleContext`, read with `useLocale()`/`useTranslation()`.
   - `shouldRevalidate`: the root reloads only after non-GET submissions or same-URL navigations.
   - `Layout`: renders `<html lang>` from the active locale's BCP 47 tag,
     wraps the app in `Analytics.Provider` → `ProfileProvider` → `PageLayout`.
   - `ErrorBoundary`: a single branded error page with a translated message chosen by
     status (404, other 4xx, 5xx); raw error messages are logged, not shown.
4. **Route loaders** query the Storefront API (`context.storefront.query`) or the Customer
   Account API (`context.customerAccount.query`). Critical data is awaited; secondary data
   (e.g. product recommendations) is returned as a promise and rendered with `<Await>`.
5. **Client-side data** for logged-in features is fetched from JSON routes (`api.*`) by
   `ProfileProvider` and `useFetcher` (see below).

## Routing

- File-based routes from `app/routes/` via `flatRoutes()` in `app/routes.ts`, wrapped by
  `hydrogenRoutes()`, which adds Hydrogen's development-only virtual routes and returns
  the routes unchanged when `NODE_ENV` is `production`.
- Naming follows React Router flat-routes: `.` = `/`, `$param`, `_index`, trailing `_` opts
  out of the parent layout (`account_.login.tsx`), `[...]` escapes characters
  (`[robots.txt].tsx`), `$.tsx` is the splat/404.
- Route types come from `./+types/<route>` (generated by `react-router typegen`).

| Area | Routes |
| --- | --- |
| Home | `_index` |
| Catalog | `collections._index`, `collections.$handle`, `collections.all`, `products.$handle` |
| Search | `search` (regular + predictive via `?predictive`) |
| Cart | `cart` (CartForm actions), `cart.$lines` (permalinks), `discount.$code` |
| Customer | `account` (layout), `account._index`, `account.profile`, `account.addresses`, `account.orders._index`, `account.orders.$id`, `account.$`, `account_.login`, `account_.authorize`, `account_.logout` |
| Personal | `favorites`, `fitting-room` |
| Language | `locale` (POST only: sets the language cookie and redirects back) |
| JSON API | `api.profile`, `api.profile.favorites`, `api.profile.fitting-room`, `api.profile.preferences`, `api.profile.preferences.export` (GET, JSON download, US-071), `api.recommendations`, `api.order-ratings` (POST only, US-058) |
| Content | `pages.$handle`, `policies._index`, `policies.$handle`, `blogs._index`, `blogs.$blogHandle._index`, `blogs.$blogHandle.$articleHandle` |
| SEO | `[robots.txt]`, `[sitemap.xml]`, `sitemap.$type.$page[.xml]` |
| Fallback | `$` (404) |

## Shopify APIs and GraphQL

- **Storefront API**: products, collections, menus, search, pages, policies, blogs, cart.
  Documents are `#graphql` template strings next to the loader that uses them (in the route
  file or an `app/lib/*.ts` module).
- **Admin API** (ratings, comments and public reviews only, US-058 to US-060): one
  server-side client, `app/lib/ratings/admin-client.server.ts` (configuration, tokens,
  timeout, Workers-safe `fetch`, code-only logs), used by `rating-store.server.ts`,
  `comment-store.server.ts` and `product-reviews.server.ts`. Documents live in
  `app/graphql/admin/` (no codegen project, so they carry no `#graphql` tag and responses are
  checked by hand). Needs `PRIVATE_ADMIN_API_CLIENT_ID`/`PRIVATE_ADMIN_API_CLIENT_SECRET` or
  `PRIVATE_ADMIN_API_TOKEN`.
- **Customer Account API**: documents live in `app/graphql/customer-account/`. They are
  a separate codegen project (see `.graphqlrc.ts`). Account routes call
  `customerAccount.handleAuthStatus()` (or use the `account` layout loader) before querying.
- **`@inContext`**: Storefront documents declare `$country`/`$language` and
  `@inContext(country: $country, language: $language)`. Hydrogen's storefront client fills
  these variables from `context.storefront.i18n` **only when the caller does not pass
  them** (verified in `node_modules/@shopify/hydrogen/dist`). Passing `language: 'EN'`
  explicitly overrides the active locale.
- **Shared fragments** (`app/lib/jeweliette-catalog.ts`):
  - `JEWELIETTE_PRODUCT_CARD_FRAGMENT`: everything a product card needs (images, options and
    swatches, price range, `custom.allergens`, `custom.product_badge`). Used by collections,
    search, favorites, fitting room and product recommendations.
  - `JEWELIETTE_RECOMMENDATION_PRODUCT_FRAGMENT`: card fields plus the traits used by the
    recommendation engine (`shopify.jewelry-material`, `shopify.watch-material`, category,
    `custom.metal`, `custom.gemstone`, `custom.gem_color`, collections).
  - `JEWELIETTE_MATERIAL_METAFIELD_FRAGMENT`: metaobject references for materials.
  - Matching TypeScript shapes: `CatalogProduct`, `CatalogProductWithTraits`.
  - Embed a fragment by interpolating it into the document (`${JEWELIETTE_PRODUCT_CARD_FRAGMENT}`).
- **Metafield parsing**: `app/lib/metafields.ts` (normalise text/list metafields),
  `app/lib/materials.ts` (material metaobjects), `app/lib/allergens.ts`,
  `app/lib/customization.ts` (customization options, see below),
  `formatMetafieldValue()` (display list metafields as comma-separated text, and treat
  `null`/`undefined` sentinels as empty). The product page hides the Description, Details and
  Materials sections when they have no content (whitespace/`&nbsp;`-only HTML, empty lists),
  so an empty metafield never renders an empty accordion.
- `app/lib/products.server.ts`: `loadProductsByIds()` loads product cards for a list of
  GIDs (`nodes(ids:)`), used by favorites and the fitting room.

## Product customization

Store admins choose which products can be customized (engraving and gem color, epic E06)
with three product metafields. The product page shows a **Customize** panel only for
products marked as customizable that have at least one valid option.

| Metafield (namespace `custom`) | Type | Meaning |
| --- | --- | --- |
| `customizable` | True or false | Turns the options on for the product. |
| `customization_gem_colors` | Single line text, **List of values** | Gem colors the shopper may choose. Shown as typed (Shopify content, translated in the admin). |
| `engraving_max_length` | Integer (min 1, max 40) | Maximum engraving length. Empty means no engraving. |

- **Admin setup:** Settings → Metafields and metaobjects → Products → Add definition. The
  key must match the table exactly (Shopify suggests one from the name; correct it), and
  each definition needs **Storefronts** access, or the Storefront API returns `null`.
- **Data flow:** `PRODUCT_CUSTOMIZATION_FRAGMENT` (`app/lib/customization.ts`) reads the
  three metafields; `PRODUCT_FRAGMENT` (`products.$handle.tsx`) and the cart check both use
  it. The loader calls `parseProductCustomization()` and returns `customization` (or
  `null`). `ProductForm` (keyed by product, so the choice resets on another product) holds
  the shopper's choice and renders `ProductCustomization.tsx` above the add-to-bag button:
  gem colors as a radio group, engraving as an input with `maxLength` and a
  remaining-characters counter.
- **Rules in `parseProductCustomization()`:** returns `null` unless `customizable` is
  `true` and at least one option is valid. Gem colors are trimmed and de-duplicated by slug
  (`value` is the slug, `label` the admin text). Engraving limits that are not positive
  integers are ignored; larger values are capped at `ENGRAVING_LENGTH_CAP` (40).
- **Cart line attributes:** `customizationAttributes()` turns the choice into cart line
  attributes, keyed by `CUSTOMIZATION_ATTRIBUTE`: `Gem color` (the admin label) and
  `Engraving` (trimmed; left out when empty). The keys are identifiers in English because
  Shopify shows them as-is at checkout and on the order. The same piece with a different
  customization becomes a separate cart line.
- **Server validation:** the `cart` action passes `LinesAdd` lines to
  `validateCartLinesCustomization()` (`app/lib/customization.server.ts`). For lines with
  customization attributes it loads the variants' product metafields (no cache) and runs
  `validateCustomizationAttributes()`: the product must be customizable, the gem color must
  be allowed, and the engraving must fit the limit and contain no control characters. Any
  failure returns 400 with an error code (`errors: [{code}]`) and leaves the cart unchanged.
  `LinesUpdate` requests that set customization attributes are rejected, because the
  storefront never changes a customization after it is added.
- **Shopping bag:** `CartLineItem` lists the gem color and engraving under the product name
  (`customizationLineDetails()`), with translated labels; the engraving is shown as typed.
- **Not done yet:** price changes for customized pieces (US-028) and the 3D preview (US-027).

## Session and cart

- `AppSession` (`app/lib/session.ts`) wraps React Router's cookie session storage: a cookie
  named `session`, `httpOnly`, `sameSite: lax`, `path: /`, signed with `SESSION_SECRET`.
  `server.ts` commits it when `isPending`. The Customer Account client keeps its tokens in
  this session under the key `customerAccount` (Hydrogen's `CUSTOMER_ACCOUNT_SESSION_KEY`).
- The cart is Hydrogen's `context.cart`. The cart ID cookie is set with
  `context.cart.setCartId()`. The `cart` route action switches on `CartForm.ACTIONS`
  (lines add/update/remove, discount codes, gift cards, buyer identity).
- The cart UI renders in two layouts (`CartMain layout="aside" | "page"`): the drawer in
  `PageLayout` and the `/cart` page. Optimistic updates use `useOptimisticCart`.

## Customer authentication

Customers sign in with **Shopify Customer Accounts** through Hydrogen's `customerAccount`
client; the storefront has no password, identity store or account linking of its own.

- `account_.login.tsx` calls `customerAccount.login()`, which redirects to Shopify's hosted
  login page. It forwards the optional `acr_values`, `login_hint`, `login_hint_mode` and
  `locale` query parameters and the storefront country.
- `account_.authorize.tsx` completes the OAuth callback; the tokens are kept server-side in
  the cookie session (see [Session and cart](#session-and-cart)).
- `account_.logout.tsx`: POST calls `customerAccount.logout()`; GET redirects home.
- `account.profile`, `account.addresses` and the `account.$` catch-all call
  `customerAccount.handleAuthStatus()` (redirect to login when signed out); the `account` layout
  and order routes go straight to `customerAccount.query()` with the session's token. The `api.*`
  profile and rating endpoints check `isLoggedIn()` and answer 401 instead.
- Which sign-in methods Shopify shows is configured in the Shopify admin, not in code; the
  store's current settings were not checked for this document. **Sign in with Google (US-078, #175) is planned and not implemented.** The
  story asks for Shopify Customer Accounts' supported Google sign-in, configured by an
  authorized administrator (Google Cloud OAuth client plus Shopify settings), keeping the
  email-code option and adding no separate identity system. Whether any storefront change
  is needed beyond configuration has not been verified.

## Customer profile: favorites, fitting room, preferences

These features are available to logged-in customers only. They are stored as JSON customer
metafields (namespace `custom`) through the Customer Account API.

| Metafield | Parser / limits | Endpoint |
| --- | --- | --- |
| `custom.favorites` | `profile/schema.ts`, max 500 GIDs | `POST /api/profile/favorites` `{add?, remove?}` |
| `custom.fitting_room` | `profile/fitting-room.ts`, max 50 **variant** GIDs (one per colourway) | `POST /api/profile/fitting-room` `{add?, remove?}` |
| `custom.preferences` | `profile/preferences.ts` (allergies, skin tone/undertone, ring sizes per finger, preferred materials/colours/gemstones) | `POST /api/profile/preferences` |

- **Fields** (Template Method): each metafield is a `ProfileField` subclass
  (`profile/profile-field.ts`). The base class's `nextValue(profile, change)` is the shared
  update algorithm (take the current value, merge the change, serialize); subclasses supply
  the steps and the metafield `key`. `ProductIdList` adds the list behaviour from
  `list-schema.ts` (dedupe, add to front, remove, cap) and is extended by `FavoritesList`
  (`schema.ts`) and `FittingRoomList` (`fitting-room.ts`), which only set the key and cap.
  `PreferencesField` (`preferences.ts`) merges a partial profile. The older functions
  (`parseFavorites()`, `applyFittingRoomOperation()`…) delegate to these instances.
- **Server** (Repository): `CustomerProfileRepository` (`profile/customer.server.ts`) reads
  the whole profile (`CUSTOMER_PROFILE_QUERY`) and `update(field, change)` writes one field
  with `metafieldsSet`, so a new profile field needs no repository change. The routes call
  `readCustomerProfile()`, `updateCustomerFavorites()`, `updateCustomerFittingRoom()` and
  `writeCustomerPreferences()`, which use the repository. `profile/operation.server.ts`
  validates list operations (method, login, JSON, product-GID format, size cap).
- **Client**: `ProfileProvider` (`profile/ProfileProvider.tsx`) loads `GET /api/profile`
  once on mount and exposes optimistic toggles. If a write returns 401, it reloads the profile.
  `useFavorites()` (`lib/favorites.ts`) and `useFittingRoom()` (`lib/fitting-room.ts`)
  are thin views over it.
- **Fitting-room gate** — the fitting room exists to try pieces on and stores **variant
  GIDs** (one entry per colourway), so a clear and a pink variant can live side by side.
  Only variants with try-on data (`resolveTryOn(product, variant)`, i.e. Earrings/Necklaces
  with a transparent overlay on the variant) can enter: the product page hides the hanger
  otherwise (`FittingRoomButton canTryOn`) and `POST /api/profile/fitting-room` validates
  the added variant ids against the Storefront API (400 with an error code otherwise).
  Sold-out variants may be viewed and tried on; only Move to cart is disabled. Removal is
  always allowed. Entries that stop being eligible (overlay removed, category changed,
  product unpublished) are **pruned when the profile loads** (`pruneFittingRoom` in
  `lib/profile/fitting-room-gate.server.ts`), and legacy product GIDs simply stop parsing
  into the variant list, so old entries disappear immediately. The prune is skipped when a
  variant still has an overlay but no recognised category: that is the signature of a
  catalogue/localization regression, and deleting the shopper's wardrobe would be worse than
  keeping an entry that cannot be tried on. If an unsupported entry still reaches the page
  (for example the overlay changed between the prune and the load), the loader returns it
  with `tryOn: null` and the view lists it with a **No 3D** marker instead of hiding it; it
  cannot be selected for a look.
- **Pages**: `/favorites` and `/fitting-room` render client-side. They call their own loader with
  `?ids=` from the profile state (`useFetcher`); favorites load product cards via
  `loadProductsByIds`, the fitting room loads variant entries via `loadVariantsByIds`
  (`lib/variants.server.ts`). The `fitting-room` action adds the **stored variant** to the
  cart and removes it from the fitting room.
- **Fitting room view** (`components/fitting-room/FittingRoomView.tsx`) lists one row per
  **variant** (product title + colour, variant image and price): rows can be selected,
  moved to the cart or removed, and sold-out rows keep Move to cart disabled. Selection is
  explicit (nothing is selected on open); the checkboxes feed the look builder on the right,
  and pieces without a model are disabled and marked **No 3D**. The look builder shows the
  selected pieces and one **Try on the look** action (`FittingRoomLookTryOn.tsx`) that opens
  a single try-on session with every selected piece that has an overlay. The look link
  carries the selected variant ids (`lookTryOnLink`), so the desktop QR reproduces the same
  set on the phone.
- **Allergens**: `useAllergenMatches()` compares product allergens with the customer's
  allergies. `AllergenBadge` and `AddToBagGuard` (a confirm dialog before adding) use it.
  The comparison only uses the product's `custom.allergens` metafield as entered in
  Shopify: a product without that data shows no warning, so the absence of a warning is not
  evidence that a piece is free of an allergen.
- **Ring sizes**: `RingSizeForm` (account) and `RingSizeHelp` (product page, ring products
  only; `profile/ringCategory.ts`).

## Front-camera try-on

A shopper can try earrings and necklaces on with the phone camera (US-017). It is not AR
surface placement: the piece is drawn on a live selfie face.

- **Gate** — `app/lib/try-on/catalog.ts`: the product's taxonomy category must be
  **Earrings** or **Necklaces** **and the selected variant** must have `custom.try_on_overlay`
  (a transparent PNG in Files). The category is matched by its taxonomy GID
  (`app/lib/taxonomy.ts`), not by `category.name`, because Shopify localises the name
  (`Earrings` → `Brincos` → `Boucles d’oreilles`); the English name is only a fallback when
  a caller has no id. There is no product-level fallback: colours are independent, so
  a product whose clear variant has an overlay and whose pink variant does not shows Try on
  (and the hanger) only for clear. `custom.try_on_size_cm` on the variant sets the piece's
  real width (default 2 cm earrings, 16 cm necklaces). Overlay URLs are loaded with
  `?cors=1` (`try-on/url.ts`) so the product page's cached `<img>` cannot taint the canvas.
  The page derives the piece from the **optimistic** selected variant, so the buttons swap
  the instant a swatch is tapped.
- **True size** — the necklace is scaled against the shopper's estimated **shoulder
  width** (`38 cm ÷ 14.5 cm` face ratio, since the FaceLandmarker has no shoulder
  landmarks), the earrings against the face width, so both keep their real proportions.
  The number cannot be derived from the image, so `custom.try_on_size_cm` must be the real
  width of the **trimmed cut-out** (a pendant-only cut-out is a few centimetres; a cut-out
  that includes the whole chain is ~40 cm). The size lives on the variant together with the
  overlay, so each colour is calibrated independently. Shoppers can still drag/resize in
  photo mode.
- **Device** — `try-on/device.ts` reads `Sec-CH-UA-Mobile` then the user agent in the
  product loader; phones open the camera dialog and computers the QR dialog. iPadOS's
  desktop user agent is refined client-side with `maxTouchPoints`.
- **Runtime** — `@mediapipe/tasks-vision` (FaceLandmarker, 478 landmarks) is imported
  lazily when the dialog opens. The classic loader (`vision_wasm_internal.js`), the WASM
  binary and the model (`app/assets/models/face_landmarker.task`) are imported with Vite's
  `?url` (`app/lib/try-on/assets.ts`), so Vite emits them under hashed `/assets/…` names
  next to the app's JS/CSS and Oxygen serves them with the right MIME type and an immutable
  cache. They used to be unversioned `public/` files; the Oxygen deployment answered a
  missing public path with its HTML 404 page, which aborts the WASM fetch with
  `both async and sync fetching of the wasm failed`. The dialog tries the GPU delegate and
  falls back to CPU. The **classic** loader is used (`vision_wasm_internal.js`, passed to
  `FaceLandmarker.createFromOptions()` in an explicit fileset): the ES-module variant is
  evaluated as a classic script and fails at runtime with `ModuleFactory not set.` The camera
  is requested **inside the shopper's tap** (`requestCamera()` is called from the button
  handler, before React updates): iOS
  Safari ties `getUserMedia` to the user gesture, so a request from an effect can be silently
  refused. QR deep links have no gesture, so they open the dialog with an "Open camera"
  button; `cameraSupport()` catches in-app browsers without `getUserMedia` and non-HTTPS
  pages. `attachCameraStream` attaches the stream to the **visible** `<video>` preview and
  starts playback without awaiting it (Safari can leave `play()` pending and then release
  the camera); an `AbortError` is retried once after `canplay`, and a track that ends is
  reported so the dialog can offer a retry. **The preview is the video element** — iOS
  releases the camera of a hidden one — and the piece is painted on a transparent canvas on
  top (`drawOverlays`); the landmarker joins later and the status reads `preparing` until
  then, because the WASM download would otherwise delay the camera by several seconds.
  `try-on/preload.ts` warms the WASM, the model and the JS chunk on idle on phones (and on
  hover/focus on desktop) **and compiles the shared landmarker** before the tap
  (`getFaceDetector()` caches one instance for the page, closed on `pagehide`), so opening
  the dialog only starts the camera. The CSP in `app/entry.server.tsx` allows
  `'wasm-unsafe-eval'` in `script-src` and `'self' blob:` in `worker-src` (MediaPipe
  compiles in a worker on some Safari versions). `attachCameraStream` sets
  `playsinline`/`webkit-playsinline`/`muted` **before** `srcObject`; the modal defers the
  camera release by one tick so React StrictMode's simulated unmount does not stop and
  reopen the hardware camera. When the camera or the WASM fails, the banner shows the
  translated message **plus the raw `Name: message`** so a phone can report the cause. A
  failed landmarker creation probes the three asset URLs (HTTP status and content type) and
  logs the result, and the banner's detail includes the short summary, so a deployment that
  serves HTML instead of the WASM is identifiable without a debugger.
- **Geometry** (`try-on/anchors.ts`, pure, pixel space): earrings are top-centre anchored at
  landmarks 177/401, pushed outwards to the lobe by `EAR_OUTWARD_RATIO` (4 % of the face
  width, along the face's lateral axis) and lifted along the face's vertical axis by
  `EAR_LOBE_LIFT_RATIO` (3 % of the face width), since the mesh's cheek point sits below the
  lobe; the ear with the smaller
  `|earX − noseX|` is hidden when the head turns (3-frame hysteresis). Necklaces anchor their
  **top centre** at the neck base (0.18 face widths below the chin) and are masked by
  MediaPipe's face oval (`evenodd`), so the chain arcs around the neck and never crosses the
  face. Jitter is
  handled in three layers: a 3-sample weighted anchor buffer (0.5/0.3/0.2, ~66 ms) rejects
  one-frame landmark spikes, an exponential filter removes the rest (90 ms; 130 ms for the
  necklace, whose chin/chest anchor is noisier), and a large jump is clamped to 15 % of the
  reference width per frame instead of teleporting. When the face is briefly lost the last
  placement is kept for 250 ms so the piece does not flicker. `try-on/frame.ts` turns one
  landmark set into **all the overlays of a look**: necklaces are planned first (longest
  first, so shorter chains sit on top), then every earring. Each planned overlay carries its
  piece id, slot (`earA`, `earB`, `necklace`) and its own smoothing reference width (face for
  earrings, shoulders for necklaces), so mixed looks filter correctly. Multiple earrings of
  the same ear are **stacked**: the first sits on the lobe and each next one is lifted by
  `EAR_STACK_GAP_RATIO` (5.5 % of the face width) along the face's vertical axis, simulating
  several piercings without any catalog change. `try-on/render.ts` paints each layer with its
  own PNG on the transparent canvas (and the full frame for photos).
- **Many pieces** — `TryOnPiece` carries the variant id, and the dialog takes `pieces[]`.
  `loadTryOnOverlays()` fetches every PNG in parallel and drops a piece whose overlay is
  opaque or cannot load, so one bad file does not block the rest of the look; when nothing is
  usable the dialog shows the unavailable/failure message. `CameraStage` and `PhotoFallback`
  read the loaded pieces from props/refs, key their smoothing state by `id:slot` and never
  restart the camera when another piece joins.
- **Photo fallback** — `PhotoFallback` decodes a picked image, switches the landmarker to
  `IMAGE` mode and composes the same overlays. Nothing is uploaded; the camera and photos
  stay in the browser. The composed look can be dragged (pointer or arrow keys) and resized
  with the − / + buttons, and "Reset position" returns to the face-based placement; this
  covers poses, crops and necklace lengths the automatic anchor cannot know. The overlay is
  checked for real transparency client-side (`try-on/overlay.ts`); an opaque PNG shows

## Recommendation engine

- `GET /api/recommendations?limit=N` (1–12, default 4); private, `no-store`.
  It returns nothing for logged-out customers or customers without favorites or preferences.
- `recommendation/catalog.server.ts` loads up to 250 best-selling candidates with
  `JEWELIETTE_RECOMMENDATION_PRODUCT_FRAGMENT` (`CacheShort`).
- `recommendation/traits.ts` turns products into `ProductTraits`.
  `recommendation/signals.ts` derives weighted signals from favorites and preferences.
  `recommendation/weights.ts` holds the trait weights.
  Skin tone and undertone: products have no skin-tone trait (`skinTones` is always empty),
  so the stored **skin tone has no effect** on suggestions (`hasRecommendationPreferences()`
  ignores it). The **undertone** is matched against a heuristic derived from the product's
  metal/colour values (`gold` → warm, `silver` → cool, `undertonesFromMetal()` in
  `traits.ts`). Try-on does not read either value.
- `recommendation/signal-source.ts` (Strategy pattern): the `SignalSource` interface
  (`collect()` returns signals) and its implementations `FavoritesSignalSource` and
  `PreferencesSignalSource`, which wrap the functions in `signals.ts`. A new kind of signal
  (e.g. recently viewed products) is a new `SignalSource`; the engine does not change.
- `recommendation/engine.ts` (pure): `RecommendationEngine` takes its signal sources plus
  options (`excludedIds`, `fallbackToPopular`) and `recommend(products, limit)`:
  1. Drops excluded products and anything matching a negative signal (allergies).
  2. Scores the rest by matching positive signals.
  3. Sorts by score, keeping catalog order on ties.
  4. Falls back to the first candidates ("Popular piece") when nothing scores and the
     fallback is enabled.

  `recommendProducts()` (used by `api.recommendations`) builds the engine with a favorites
  and a preferences source, excludes the favorites and enables the fallback only when there
  are favorites.
- UI: `components/product/RecommendedProducts.tsx` fetches the endpoint with `useFetcher`.
  Product pages also show Shopify's `productRecommendations` (separate query in
  `products.$handle.tsx`).

## Order ratings (US-058)

A signed-in shopper gives each distinct product of a **fully delivered** order a 1–5 star
rating from the order page (`/account/orders/:id`). A rating is final: it can be read back
but never changed, replaced or deleted by the storefront.

### Approved rules and requirement clarification

The project owner approved these rules on 2026-11-20 to resolve "Verified-buyer rule to
confirm (see Q2)" in issue #79. Q2 itself is not written down in the issue or in this
repository; the decision below is the reference.

- **Entry point:** the order-detail page in the Hydrogen account area. The original
  acceptance criterion says "when I open its page" (the product page); the owner approved
  the order page instead. The product page has **no** rating control, and the issue text was
  not changed.
- **Who:** only a signed-in customer. Identity comes from the Customer Account session on
  the server; customer IDs, emails or "verified" flags sent by the browser are ignored. The
  order must be one that Shopify returns for that customer's account when the rating is
  made (Shopify returns `null` for anyone else's order). There is no email matching.
- **When:** only after the **whole order** is confirmed delivered (predicate below).
  Payment status, refunds and returns are **not** part of the rule: they are neither
  queried nor checked, a later return or refund does not remove the right to rate, and it
  does not change or delete a saved rating.
- **What:** exactly one rating per customer + order + distinct product (grouped by Shopify
  product ID; several units or variants of a product give one rating). The same product in
  another delivered order can be rated again for that order. Lines without a product ID
  (deleted products, custom items) cannot be rated.
- **Later stories:** comments (US-059) and showing ratings, averages and comments to other
  shoppers (US-060) are described in
  [Rating comments and product reviews](#rating-comments-and-product-reviews-us-059-us-060).
  Still out of scope: sorting/filtering (US-061), a moderation screen in the app (US-062;
  comments are reviewed in the Shopify admin for now), store feedback (US-063). No
  `reviews.rating`/`reviews.rating_count` metafields are written.

### Delivery predicate

`isOrderFullyDelivered()` (`app/lib/ratings/delivery.ts`), from Customer Account API data:

1. `Order.fulfillmentStatus` is `FULFILLED` (necessary, not sufficient), and
2. every line item with a quantity is covered, unit for unit, by fulfillments whose
   `status` is `SUCCESS` **and** whose `latestShipmentStatus` is `DELIVERED`
   (`fulfillmentLineItems.quantity` summed per line, so split shipments count only when
   each one is delivered).

Not accepted as delivery: `FULFILLED` alone, a `SUCCESS` fulfillment without a shipment
status, tracking information, estimated delivery dates, elapsed time, `PICKED_UP` (local
pickup) and any other shipment status. Missing quantities count as zero. Fulfillments that
are cancelled, failed, pending or open add nothing, so a split order stays locked until
every shipment holding one of its units is delivered. No payment, refund or return data is
queried (`financialStatus`, `refunds`, `refundableQuantity` are not in the documents).

Fields used (Customer Account API schema shipped with Hydrogen 2026.4):
`Order.fulfillmentStatus` (`OrderFulfillmentStatus`), `Order.lineItems { id productId quantity }`,
`Order.fulfillments { status (FulfillmentStatus) latestShipmentStatus (FulfillmentEventStatus)
fulfillmentLineItems { quantity lineItem { id } } }`. All three connections are paged to the
end; an error, a missing cursor or more than 20 pages fails closed as "could not verify"
(never as "not delivered").

**Local pickup is out of scope** for US-058: pickup orders cannot be rated. Supporting them
would need an owner decision on whether `PICKED_UP` counts as delivery.

Known limits of this predicate (they fail closed: the order cannot be rated):
- Delivery is only known when the carrier or the merchant records a `DELIVERED` shipment
  event. Shipments without carrier tracking need the merchant to mark them delivered in
  the Shopify admin.
- Local pickup orders and lines that are never shipped (e.g. digital items or units
  removed before shipping, if Shopify still counts them in `quantity`) block the order.
- A shipment status that later moves away from `DELIVERED` makes the order unratable
  again; ratings already saved stay visible.

**Reading is separate from authorizing.** The order page reads saved ratings for every
product of the order whatever its current line quantity or delivery state (e.g. after a
return), and shows them read-only. Only products whose line has a quantity, in an order
that passes the predicate, get a rating form or are accepted by the endpoint. Saved ratings
are hidden only when the order itself cannot be loaded (Shopify error or page limit); the
section then shows the verification error.

### Flow

| Step | Code |
| --- | --- |
| Order page loader returns `ratings` as a promise (the order renders first; `<Suspense>` shows "Checking…") | `routes/account.orders.$id.tsx` → `loadOrderRatings()` |
| Order lines, fulfillments and fulfillment items, every page (100 lines, 20 fulfillments, 100 items per page; more than 20 pages of any of them fails closed) | `lib/ratings/order-eligibility.server.ts`, `graphql/customer-account/CustomerOrderRatingQueries.ts` |
| Group lines by product; validate the submission | `lib/ratings/rating.ts` |
| Saved ratings read by exact handle | `lib/ratings/rating-store.server.ts` |
| Form: radio group per unrated product, then read-only stars | `components/account/OrderRatings.tsx`, `StarRating.tsx` |
| After a save: no reload of the order page. Its `shouldRevalidate` returns `false` only for POSTs to `/api/order-ratings` (201 and 409 alike), so the form shows the saved or existing value with its confirmation and other products keep unsaved choices; every other action, navigation and reload uses React Router's default | `routes/account.orders.$id.tsx` |
| Save: `POST /api/order-ratings` `{orderId, productId, rating}` (JSON) | `routes/api.order-ratings.tsx` → `submitRating()` (`lib/ratings/ratings.server.ts`) |

`POST /api/order-ratings` checks, in this order: method (405), same-origin (403
`cross_origin`), login (401), store configured (503 `ratings_unavailable`), JSON and payload
(400: `rating` must be a JSON integer 1–5, IDs must be Shopify GIDs), then loads the order
again from Shopify: not the customer's (404 `order_not_found`), product not in it (422),
not fully delivered (403 `not_delivered`), Shopify unavailable (503
`verification_unavailable`). Then it creates the record: 201 `{productId, rating}`, or 409
`already_rated` with the existing value, or 503 `save_failed`. Every response is
`Cache-Control: no-store`, `Vary: Cookie`; so is the order page (`headers` export).

**Same-origin check** (`lib/request-origin.server.ts`): when the browser sends
`Sec-Fetch-Site` (set by the browser, not by page scripts), only `same-origin` is accepted;
`same-site`, `cross-site` and `none` are rejected. If `Origin` is sent as well, its host must
be the host the worker sees; a foreign or opaque (`null`) `Origin` next to `same-origin` is
treated as forged and rejected (a browser reporting `same-origin` always sends its own
origin). The scheme is not compared in that case: a real scheme difference is a different
origin, which the browser would not report as `same-origin`. Without `Sec-Fetch-Site` (older
browsers) the `Origin` header must equal the request's own origin exactly. With neither
header the request is rejected, so only non-browser clients are affected. No proxy headers
(`X-Forwarded-*`) are trusted and no CORS is granted. `Sec-Fetch-Site` is checked first because the worker
can see a different URL than the browser: behind the Hydrogen dev tunnel (and any proxy that
terminates TLS) the worker sees `http://…` while the page's `Origin` is `https://…`, and an
`Origin`-only comparison rejected genuine submissions (found in the first real browser test).

### Storage: private metaobjects

Ratings are `product_rating` metaobjects written through the **Admin GraphQL API**
(`ADMIN_API_VERSION` `2026-04`) by a server-only adapter, `ShopifyRatingStore`. Credentials
and tokens never reach the browser and are not logged. Tokens come from
`lib/ratings/admin-token.server.ts`: either a static legacy token, or a client credentials
exchange (`POST https://<shop>.myshopify.com/admin/oauth/access_token`, form-encoded
`grant_type=client_credentials`, `client_id`, `client_secret`) whose 24-hour token is cached
per worker instance and renewed one minute before expiry; a 401 from the Admin API drops
the cached token.

| Field key | Type | Value |
| --- | --- | --- |
| `customer_id` | Single line text | Customer GID from the Customer Account API |
| `order_id` | Single line text | Order GID |
| `product_id` | Single line text | Product GID |
| `rating` | Integer (min 1, max 5) | Stars |

Nothing else is stored (no names, emails, prices or addresses). Shopify keeps its own
creation and update times for each entry.

**Uniqueness and immutability: UNRESOLVED until verified on staging.**

The handle is `rating-` + SHA-256 of `customerId|orderId|productId`. The adapter never calls
`metaobjectUpsert` or `metaobjectUpdate`, so it never overwrites a record itself. Whether
Shopify keeps **one** record per handle is the open question:

| Fact | Source |
| --- | --- |
| Handles are "unique identifiers within a metaobject type" | Admin API reference, `metaobjectByHandle` and `metaobjectUpsert` pages (read for 2026-07) |
| `metaobjectCreate` "generates a unique handle automatically if you don't provide one"; `MetaobjectCreateInput.handle` is "auto-generated when omitted" | 2026-04 reference (the pinned version) |
| What `metaobjectCreate` does with an **explicitly supplied** handle that already exists (an error, and which code, or a different handle) | **Not documented** for 2026-04. `MetaobjectUserErrorCode.TAKEN` ("The input value is already taken") exists, but no page ties it to handles. Product-handle behaviour (`productCreate`) is not evidence for metaobjects. |
| Concurrency or idempotency of `metaobjectCreate` | Not documented |

What the adapter does with each answer (`rating-store.server.ts`):
- record returned **with the requested handle**: saved (201);
- **no record** (any `userErrors`, e.g. `TAKEN`, or none): it reads the exact handle; an
  existing record is reported unchanged (409 `already_rated`), otherwise the save failed
  (503);
- record returned **with another handle**: Shopify stored a second record. The adapter logs
  `uniqueness violation`, tries to delete that record and reports the one under the exact
  handle. **This compensation is not a guarantee**: the delete can fail, or the worker can
  stop before it runs, leaving two records (reads still show only the exact-handle one).

Uniqueness therefore holds **only if** Shopify atomically rejects a create whose explicit
handle exists, including under concurrency. The service does not read before creating, so
every retry and concurrent submission really reaches `metaobjectCreate`. Staging checks A1
and A2 below decide this. **If Shopify stores the duplicate under another handle, this
storage does not meet the requirement.** The smallest alternative to evaluate (it needs
approval) is `metafieldsSet` with `compareDigest`, which Shopify documents as an atomic
compare-and-set (although "create only if absent" with a `null` digest is not stated
explicitly), on an owner the app is allowed to write. That changes scopes and storage, so it
is not implemented.

Reads use `metaobjectByHandle` with the exact handle and check that the stored IDs match the
key.

### Shopify setup (manual, by a store admin)

Nothing is created automatically.

1. **Metaobject definition:** Settings → Custom data → Metaobjects → Add definition.
   - Name `Product rating`, type (API handle) **`product_rating`**.
   - Fields as in the table above, with exactly those keys; on `rating` set the validations
     minimum 1 and maximum 5. Make all fields required.
   - Two separate access settings:
     - **Admin API access: `PUBLIC_READ_WRITE`** ("merchant and other apps can read and
       write"). Required: with `MERCHANT_READ_WRITE` or `MERCHANT_READ`, Shopify gives other
       apps no access, so the ratings app could neither save nor read entries. This only
       concerns authenticated Admin API apps installed on the store, not shoppers.
     - **Storefronts access: off** (`NONE`). This is the public Storefront API; it must stay
       off so rating records are never readable from the storefront.
   - Turn off *Active-draft status* (publishable), *Translations* and *Web pages* (online
     store); a rating has no draft state, nothing to translate and no public page.
   - To check the result without the admin UI, an app with `read_metaobject_definitions`
     can query `metaobjectDefinitionByType(type: "product_rating") { access { admin
     storefront } fieldDefinitions { key required type { name } validations { name value } } }`.
     The ratings code itself does not need that scope.
2. **App with Admin API access.** Scopes: **`read_metaobjects`, `write_metaobjects`** only
   (no product, order or customer scopes). Two options:
   - **Dev Dashboard app (new apps since 2026-01-01).** Shopify no longer lets admins create
     new custom apps in the store admin. Create the app in the Dev Dashboard, select the two
     scopes on the app version, release it and install it on the store. The client
     credentials grant only works when **the app and the store belong to the same Shopify
     organization** (a dev store must be created from the Dev Dashboard to be in it). Copy
     the client ID and client secret.
   - **Existing legacy custom app** (created in the admin before 2026-01-01): give it the
     two scopes and use its Admin API access token.
3. **Environment** (Oxygen: Hydrogen storefront → Storefront settings → Environments and
   variables, marked secret, for staging and production; local `.env` if needed). Set
   `PRIVATE_ADMIN_API_CLIENT_ID` and `PRIVATE_ADMIN_API_CLIENT_SECRET` (Dev Dashboard app),
   **or** `PRIVATE_ADMIN_API_TOKEN` (legacy app; it wins if both are set).
   `PUBLIC_STORE_DOMAIN` must be the `*.myshopify.com` domain. Without credentials, the order
   page shows "Ratings are not available at the moment." and the endpoint answers 503.
4. **Credential lifecycle:** keep secrets only in Oxygen secrets and local `.env`
   (git-ignored). Rotate the Dev Dashboard client secret there (or the legacy token by
   reinstalling the app), update the Oxygen variables and redeploy; exchanged tokens expire
   within 24 hours on their own. Uninstall the app to revoke access. Never paste secrets
   into issues, PRs, logs or docs.
   **If the store is not in the same organization as a Dev Dashboard app**, the client
   credentials grant is not available; that would need an OAuth install flow, which this
   story does not implement.

`tests/staging/rating-storage.staging.ts` only writes `product_rating` entries with synthetic
IDs (`gid://shopify/Customer/0`, `gid://shopify/Order/0`, and product IDs unique to the run),
deletes only that run's entries at the end (never another run's probes) and prints Shopify's

## Rating comments and product reviews (US-059, US-060)

A shopper who has rated a product of a delivered order can write a comment about it on the
order page (US-059). The comment is saved as a **draft** and appears on the product page only
after the team publishes it in the Shopify admin. The product page shows the average and the
number of **all** verified ratings, plus the published comments (US-060).

### Decisions (2026-11-20)

- **Who can comment:** only the signed-in customer, on their own rating. The endpoint loads
  the order again with the customer's session (ownership), checks that the product is in it
  and that a rating is saved for that customer, order and product. Delivery is not checked
  again: a saved rating already required it.
- **One comment per rating, editable.** Unlike the stars, the comment can be changed. Every
  save, new or edited, goes back to review (draft), so an edited comment is hidden from the
  product page until it is published again.
- **Validation:** after trimming, normalising line breaks and removing control characters,
  the comment must not be empty and must have at most **1000 characters** (Unicode code
  points, so an emoji counts as one). The client checks the same rule
  (`lib/ratings/comment.ts`) so the shopper gets the message at once; the server decides.
- **Review:** Shopify's *active/draft status* on the `product_review_comment` definition.
  Draft = in review, active = published. The team publishes or hides comments in the Shopify
  admin (Content → Metaobjects). There is no moderation screen in the app (US-062).
- **Product page:** average (one decimal) and count of every verified rating of the product,
  with or without a comment. Comments: only published ones, newest first, at most 20, each
  with its stars, text, "Verified buyer" and the date of its last change. No names, customer
  or order IDs are shown or sent to the browser. Without ratings, the page invites the first
  review and links to `/account/orders`.

### Flow

| Step | Code |
| --- | --- |
| Order page: saved comment and status per rated product (read with the ratings) | `routes/account.orders.$id.tsx` → `loadOrderRatings()` → `CommentStore.findComments()` |
| Comment form (add / edit, counter, review state) | `components/account/RatingComment.tsx`, inside `OrderRatings.tsx` |
| Save: `POST /api/rating-comments` `{orderId, productId, comment}` (JSON) | `routes/api.rating-comments.tsx` → `submitComment()` (`lib/ratings/ratings.server.ts`) |
| Product page: reviews as a deferred promise (the page renders first) | `routes/products.$handle.tsx` → `loadProductReviews()` (`lib/ratings/product-reviews.server.ts`) |
| Average | `listProductRatingValues()` (`rating-store.server.ts`), `summarizeRatings()` (`reviews.ts`) |
| Published comments | `CommentStore.listPublished()` (`comment-store.server.ts`) |
| Reviews section | `components/product/ProductReviews.tsx` (reuses `StarRatingValue`) |

`POST /api/rating-comments` checks, in this order: method (405, `Allow: POST`), same-origin
(403 `cross_origin`, same rule as ratings), login (401), Admin configured (503
`ratings_unavailable`), JSON and payload (400 `invalid_json`, `invalid_payload`,
`invalid_order`, `invalid_product`, `empty_comment`, `comment_too_long`), then the order:
not the customer's (404 `order_not_found`), product not in it (422), Shopify unavailable
(503 `verification_unavailable`), no saved rating (409 `not_rated`). Then it upserts the
comment as a draft: 200 `{productId, comment: {text, status: 'in_review'}}`, or 503
`save_failed`. Every response is `Cache-Control: no-store`. The order page does not reload
its data after a comment is saved (`shouldRevalidate`), as for ratings.

The product page loader reads reviews through `context.withCache` (the worker cache, added
in `app/lib/context.ts`) with `max-age=60, stale-while-revalidate=240`: a published comment
or a new rating appears within about a minute (up to five while stale). Only complete
results are cached; errors are not. On mock.shop or without Admin credentials the section
says reviews are not available.

### Storage

**Comments** are `product_review_comment` metaobjects written with `metaobjectUpsert` under
the handle `comment-` + the same SHA-256 as the rating (`commentHandle()` in `rating.ts`),
so there is at most one comment per rating. Every upsert sends
`capabilities.publishable.status: DRAFT`; the adapter refuses a save that Shopify reports as
published. Reads by exact handle check that the stored IDs match the key.

| Field key | Type | Value |
| --- | --- | --- |
| `customer_id` | Single line text | Customer GID |
| `order_id` | Single line text | Order GID |
| `product_id` | Single line text | Product GID (**filterable**) |
| `rating` | Integer (min 1, max 5) | Copy of the stars (ratings never change, so the copy cannot go stale) |
| `comment` | Multi-line text (max 1000 characters) | The comment |

**Public listings** use `metaobjects(type:, query: "fields.product_id:\"<gid>\"")`. This
filter only works on fields marked **filterable** in the definition (Admin API, since
2025-10), so `product_id` must be filterable on both `product_rating` and
`product_review_comment`. The ratings listing selects only `product_id` and `rating`
(aliased `field(key:)`), never customer or order IDs. More than 20 pages of 250 ratings fail
closed (the section shows an error) rather than show an average of part of the ratings.
Comments are read newest first (`sortKey: "updated_at"`, at most 4 pages) and filtered to
published ones in code.

### Shopify setup for comments and reviews (manual, by a store admin)

In addition to the [ratings setup](#shopify-setup-manual-by-a-store-admin):

1. **`product_rating`:** edit the definition and mark `product_id` as **filterable** in the
   admin (the `adminFilterable` capability). Without it the product page shows "We couldn't
   load the reviews right now".
2. **New definition `product_review_comment`** (Settings → Custom data → Metaobjects):
   - name `Product review comment`, type **`product_review_comment`**, the fields in the
     table above with exactly those keys, all required; `rating` min 1 max 5; `comment`
     maximum 1000 characters; `product_id` **filterable**;
   - **Active-draft status on** (this is the review state);
   - Admin API access `PUBLIC_READ_WRITE`, **Storefronts access off** (`NONE`): the record
     holds the customer ID;
   - translations and web pages off.
3. The app keeps the scopes `read_metaobjects` and `write_metaobjects`; nothing else.
4. **Reviewing:** Content → Metaobjects → Product review comment. Set an entry to *Active*
   to publish it, back to *Draft* to hide it. A customer edit sets it to draft again.

### Staging verification for comments and reviews (manual)

1. Do the setup above.
2. Signed in, on a delivered order with a saved rating: add a comment. The page shows it with
   "In review"; after a reload it is still there. An empty or 1001-character comment shows a
   message and is not saved.
3. The product page still shows no comment. In the admin, set the entry to Active; within a
   minute or so the product page shows it with the stars, "Verified buyer" and the date, and
   the average and count include every rating of the product.
4. Edit the comment on the order page: it shows "In review" again and disappears from the
   product page (after the cache expires) until it is published again.
5. A product without ratings shows the invitation and the link to the orders page.

## Testing

See [testing.md](testing.md). In short:
- `tests/unit`: Vitest in node, for `app/lib` and API route loaders/actions.
- `tests/components`: Vitest in jsdom with Testing Library.
- `tests/e2e`: Playwright on desktop Chromium against `npm run preview`.
- CI (`.github/workflows/test.yml`): the `test` job runs lint, typecheck and
  `npm run test:coverage` (unit/component tests with coverage thresholds); the `e2e` job runs
  against mock.shop.

## Generated types

- `npm run codegen` runs `shopify hydrogen codegen` (Storefront →
  `storefrontapi.generated.d.ts`, Customer Account → `customer-accountapi.generated.d.ts`) and
  `react-router typegen` (route `+types`). `dev` and `build` run codegen too.
- Query result types are named after the operation (`query Header` → `HeaderQuery`), and
  fragments likewise (`JewelietteProductCardFragment`).
- Never edit the generated files. Commit them after running codegen.
