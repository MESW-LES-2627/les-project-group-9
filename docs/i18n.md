# Internationalisation (i18n)

The store must be usable in English (EN-US), European Portuguese (pt-PT) and French
(fr-FR). Stories: **US-046** (switch between PT, EN-US and FR), **US-047** (all text in the
chosen language).

> **Status:** language selection (US-046) and the interface text of the storefront
> (US-047) are available in EN, PT and FR. Shopify content (products, collections, menus,
> pages, policies, blogs, metafields) is translated in the Shopify admin, not in code; until
> Portuguese and French are published there, that content appears in English. See
> [Shopify administration setup](#shopify-administration-setup) and
> [What is not translated in code](#what-is-not-translated-in-code).

## Languages

Defined once in `LOCALES` (`app/lib/i18n.ts`). The app code, the Shopify `LanguageCode`
and the BCP 47 tag are three different values; do not use one in place of another.

| App code (cookie, form) | Shopify `LanguageCode` | BCP 47 tag (`<html lang>`, `Intl`, Accept-Language) | Name |
| --- | --- | --- | --- |
| `en` (default and fallback) | `EN` | `en-US` | English (US) |
| `pt` | `PT_PT` | `pt-PT` | Português (Portugal) |
| `fr` | `FR` | `fr-FR` | Français (France) |

**Portuguese code check.** The installed Storefront schema
(`@shopify/hydrogen/dist/storefront-api-types.d.ts`) has three Portuguese codes: `PT`
("Portuguese"), `PT_BR` ("Portuguese (Brazil)") and `PT_PT` ("Portuguese (Portugal)"). The
app uses `PT_PT`. The store's `localization.availableLanguages` currently lists only `EN`
(2026-11-11), so the store-side code cannot be confirmed yet. **After Portuguese (Portugal)
is published, check that `availableLanguages` lists `PT_PT`.** If it lists `PT`, change
`LOCALES.pt.language`.

**French code check.** The installed Storefront and Customer Account schemas have a single
French code, `FR` (no regional variants), so the app uses `FR`. The store does not list it
yet (2026-11-11). **After French is published, check that `availableLanguages` lists `FR`.**

**French formatting convention.** The French experience uses France, `fr-FR`, for
`<html lang>`, `Intl` formatting and plural rules (e.g. `1 234,5`; plural `one` for 0 and 1).
Other French-speaking regions (`fr-CA`, `fr-BE`, `fr-CH`…) get this experience through
primary-language matching; there are no regional French variants.

**Source language.** English (`en`) is the shop's primary language and its only published
language. This was confirmed by a read-only Admin API check by the project owner
(2026-11-11): the four market web presences all have `en` as default locale and no
alternate locales; shop country Portugal, currency EUR. The Storefront API agrees
(`availableLanguages` lists only `EN`). So the fallback for missing translations is
English.

The previous subdomain detection (`es.`/`fr.`/`de.`/`jp.` → ES/FR/DE/JA, which also changed
the country) was removed in US-046. Nothing else depended on it apart from its unit tests.

## Language and country

Language and commercial country are separate settings.

- **Language**: resolved per request as described below.
- **Country**: always `DEFAULT_COUNTRY` = `US`, the template default this project already
  used before US-046. It never follows the language and is never inferred from
  Accept-Language. It is sent as `@inContext(country:)`, to analytics consent, and to
  Customer Account login (`countryCode`).
- **Store configuration (Storefront API, 2026-11-11):** a single market, Portugal (`PT`,
  EUR). A `@inContext(country: US)` query returns `localization.country = PT` and EUR prices,
  so Shopify resolves the unknown country to that market.
- What this does and does not show: language changes leave the country variable unchanged,
  and the E2E test checks that the cart cookie and the displayed currency symbol survive a
  switch. It does **not** prove checkout behaviour (checkout locale, tax, shipping) for the
  `US` value; that was not tested.
- **Configuration follow-up** (separate task; not part of US-046/US-047 and not US-048):
  English being the default *language* does not mean the commercial country must be `US`.
  Decide whether `DEFAULT_COUNTRY` should stay `US` or match the store's Portugal market
  (`PT`). Changing it affects `@inContext(country:)`, analytics consent, Customer Account
  login and possibly checkout. US-046 keeps the existing `US` behaviour on purpose.

## How the active language is resolved

Precedence (`resolveLocale()` in `app/lib/i18n.ts`, run on the server for every request):

1. **Explicit choice**: a valid `jeweliette_locale` cookie (`en`/`pt`/`fr`), set only by the
   language selector.
2. **Browser preference**: the best supported language in the `Accept-Language` header.
3. **English.**

An invalid or unsupported cookie value is ignored, so negotiation still applies. Browser
negotiation **never sets a cookie**: until the shopper chooses, each request follows the
browser's current preference. Once they choose, the cookie wins on every later navigation and
reload, whatever the browser sends.

The language is resolved on the server before rendering, so the HTML, `<html lang>`, the
Shopify content and the hydration data always agree; nothing switches after hydration.

### Accept-Language negotiation

`parseAcceptLanguage()` + `negotiateLocale()`:

- Entries are ordered by quality (`q`), keeping header order for equal qualities.
- `q=0` means "not acceptable", so those entries are excluded.
- Malformed entries (invalid range or `q`) are skipped; valid entries next to them still
  count. Missing, empty, wildcard-only (`*`) and fully malformed headers give no match.
  Headers are capped at 1024 characters and 32 entries.
- Tags are compared case-insensitively. For each preference in order: an exact tag match
  wins (e.g. `pt-PT`), otherwise the first supported locale with the same primary language
  (`pt`, `pt-BR` → `pt`; `en`, `en-GB` → `en`; `fr`, `fr-CA`, `fr-BE` → `fr`). `*` names no
  specific language and is skipped.
- **pt-BR**: mapped to the European Portuguese experience, because it is the only
  Portuguese translation available. There is no separate Brazilian Portuguese
  implementation. If a `pt-BR` locale is added later, the exact match will select it.
- No supported match → English.

| Cookie | Accept-Language | Result |
| --- | --- | --- |
| — | `pt-PT,pt;q=0.9,en;q=0.8` | `pt` (browser) |
| `en` | `pt-PT,pt;q=0.9,en;q=0.8` | `en` (cookie) |
| `pt` | `en-US` | `pt` (cookie) |
| — | `fr-FR,fr;q=0.9,en;q=0.8` | `fr` (browser) |
| — | `fr-CA` | `fr` (browser) |
| `en` | `fr-FR,fr;q=0.9` | `en` (cookie) |
| `fr` | `pt-PT` or `en-US` | `fr` (cookie) |
| — | `de;q=1,fr;q=0.8,pt;q=0.7,en;q=0.5` | `fr` (browser) |
| — | `de;q=1,pt;q=0.8,en;q=0.5` | `pt` (browser) |
| — | `de-DE,de;q=0.9,en;q=0.8` | `en` (browser) |
| — | `pt;q=0, en` | `en` (browser) |
| `de` or `FR` (invalid) | `pt-PT` | `pt` (browser) |
| — | missing, `*` or malformed | `en` (default) |

### Request flow

```
POST /locale  (locale=pt, redirectTo=/current/path?query#hash)
  └─ validates locale (isLocaleCode) and redirectTo (toSafeRedirectPath, same-origin only)
  └─ 302 → redirectTo, Set-Cookie: jeweliette_locale=pt; Path=/; Max-Age=31536000;
                                   HttpOnly; SameSite=Lax; Secure (HTTPS only)
every request
  └─ server.ts → createHydrogenRouterContext → getLocaleFromRequest(request)
       └─ resolveLocale(): cookie → Accept-Language → 'en'
       └─ i18n = {language: 'PT_PT', country: 'US'}
            → context.storefront.i18n, context.customerAccount.i18n
  └─ root loader returns locale = toAppLocale(storefront.i18n) = {code, language, country, tag}
  └─ <html lang={locale.tag}>
```

- `app/routes/locale.tsx` is the only way to change the language. It accepts POST only
  (GET → 405 `Allow: POST`). An unsupported `locale` → 400 and no cookie. An invalid,
  absolute or protocol-relative `redirectTo` → redirect to `/` (no open redirects).
- `finalizeResponse()` (`app/lib/response.server.ts`, called by `server.ts`) **appends** the
  session `Set-Cookie` header instead of replacing it, so the language cookie survives when
  the session is also committed on the same response (`tests/unit/response.test.ts`).

### Caching

The HTML and `.data` responses depend on the `Cookie` and `Accept-Language` request
headers. What was checked:

- **Our responses**: `entry.server.tsx` sets only `Content-Type` and the CSP; no route sets a
  shared-cacheable `Cache-Control` on HTML or loader data. Only `robots.txt` and the
  sitemaps set `max-age`, and the API routes use `no-store`. So nothing in the app marks a
  page as storable by a shared cache.
- **Change in US-046**: `finalizeResponse()` adds `Vary: Cookie, Accept-Language` to every
  app response, merged with any existing `Vary` and leaving `Vary: *` alone. Any cache that
  stores a response must key it on those headers, so one shopper's language cannot be served
  to another. Effect: no change today (nothing is shared-cached), and safe if page caching
  is ever added. Cookie-varied responses are in practice not shared, which is intended for
  personalised pages. An E2E test checks the header on real document responses.
- **Shopify data**: Hydrogen's subrequest cache key includes the query body and variables,
  so `$language` separates cached Storefront results per language (verified in the
  Hydrogen source and by `tests/unit/locale-propagation.test.ts`). Header and footer menus
  use `CacheLong`, so a menu translated in Shopify can take up to an hour to appear on a
  running server.
- **Oxygen**: whether Oxygen's edge caches full pages without an explicit
  `Cache-Control`, and whether it honours `Vary`, was not verified (**unverified**). Local
  tests run on MiniOxygen (`npm run preview`) and prove nothing about the deployed cache. Do
  not add public page caching without checking this first.

2. Fetch a page with `Cookie: jeweliette_locale=en` and `Accept-Language: fr-FR`, and with

## Language selector

`LanguageSelector` (`app/components/layout/LanguageSelector.tsx`) is one dropdown used in
both header modes. It is a `<Form method="post" action="/locale">` containing a native
`<details>` disclosure:

- **Trigger** (`<summary>`): flag + short code of the current language (`EN`, `PT`, `FR`)
  and a chevron. Its accessible name starts with the visible code and adds the localized
  current language, e.g. "PT, Idioma atual: Português (Portugal)".
- **Panel**: a list (labelled "Language" / "Idioma" / "Langue") with one ordinary submit
  button per `LOCALES` entry: flag, short code and the language's own name ("English (US)",
  "Português (Portugal)", "Français (France)", each with its own `lang`). The current one
  has `aria-current="true"` and a check mark. A hidden `redirectTo` keeps the current
  path, query and hash.
- **Pattern**: native disclosure semantics. There are no menu or listbox roles, so screen
  readers announce a disclosure plus a list of buttons, and Tab moves through them.
  Enter/Space on the trigger open and close it natively. With JavaScript it also supports
  ArrowDown/ArrowUp (open, move, wrap), Home/End, Escape (closes, returns focus to the
  trigger, and does not close the mobile drawer), closing on outside click, when focus
  leaves the control, and after a choice.
- **Without JavaScript** the `<details>` still opens and the buttons still post, so the
  language can be changed before hydration.
- **Flags** are small inline SVGs in the same file (US, PT, FR), `aria-hidden`. They are
  not emoji (Windows shows flag emoji as letters) and need no external requests. The flag
  key lives in `LOCALES`.
- **Placement**: in the desktop header (≥ 1280px) as a popover below the trigger, layered
  inside the sticky header (`z-50`) and under the drawers (`z-[70]`). In the compact
  header (< 1280px) it sits at the bottom of the menu drawer and expands inline, so it
  cannot be clipped. The drawer closes after a choice. See
  [responsive.md → Site header modes](responsive.md#site-header-modes).
- **Targets**: trigger and options are at least 44×44 px, set in explicit pixels because
  `rem` sizes shrink with the 14px root font.
- With JavaScript, React Router submits the action and revalidates the root and page loaders
  and any loaded fetchers, so the page re-renders in the new language without a full reload.
  This is browser-verified for page data and the predictive-search fetcher. For the
  favorites, fitting-room and recommendation fetchers it is inferred from code and not
  verified in an authenticated browser.

### What a language change visibly changed before US-047 (historical)

Checked in Chromium after switching EN to PT on the home page: the cookie is set,
`<html lang>` becomes `pt-PT`, and every translated label changes. On the desktop header
the only *visible* text that changed was the skip link (shown only on keyboard focus). The
rest are `aria-label`s on icon buttons, plus the selector's own code. Menu titles come from
Shopify (English only), and the announcement bar, page content and footer were hardcoded
English. That is why switching looked like it did nothing; US-047 translates the
hardcoded text.

Since US-047 all interface text goes through the dictionaries, so switching language
changes the visible page immediately (announcement bar, navigation fallbacks, page copy,
buttons, forms, errors, page titles, prices and dates). Shopify content changes only once
the language is published and translated in Shopify.

## Reading the language in code

| Where | How |
| --- | --- |
| Loaders and actions | `context.storefront.i18n` / `context.customerAccount.i18n` (`{language, country}`) |
| Components | `useLocale()` → `{code, language, country, tag}`. The root layout puts the root loader's `locale` into `LocaleContext`; outside that provider (isolated component tests) it is English. Wrap a component in `<LocaleContext.Provider value={…}>` to test another language. |
| UI text | `const t = useTranslation(); t('nav.search')`; values: `t('nav.openCart', {count})` |
| Loaders and actions (messages shown to the shopper) | `translatorFor(context.storefront.i18n)` or `translatorFor(context.customerAccount.i18n)` |
| Route `meta` functions | `translatorFromMatches(matches)` (reads the locale from the root match) |
| Outside React | `createTranslator(code)` |
| Prices | `<Money data={…}>` from `app/components/shared/Money.tsx` (not Hydrogen's), or `formatMoney(money, tag)` |
| Dates | `formatDate(value, tag)` |
| Lists ("A, B and C") | `formatList(items, tag)` |

## UI messages

- Messages live in `app/lib/messages/en.ts`, `pt.ts` and `fr.ts`. `en.ts` defines the key
  set (`MessageKey`) and each message's shape (string or plural object). The other languages
  are typed against it, so **a missing or extra key, or a plural message given as a plain
  string, fails `npm run typecheck`**. `tests/unit/messages.test.ts` also checks that no
  message is empty, that placeholders match and that no key is unused. At runtime a missing key falls back to
  English.
- Keys are grouped by module with a prefix: `language.`, `nav.`, `common.`, `layout.`,
  `menu.`, `footer.`, `policy.`, `search.`, `home.`, `catalog.`, `filters.`, `price.`,
  `product.`, `allergen.`, `allergy.`, `ring.`, `recommendation.`, `cart.`, `favorites.`,
  `fittingRoom.`, `account.`, `orders.`, `order.`, `address.`, `profile.`, `preferences.`,
  `meta.`, `error.`, `policies.`.
- **Identifiers are never translated**: handles, IDs, URLs, enum values, stored preference
  ids, cookie values. Translate the label for an identifier with a key built from it, e.g.
  `` t(`allergen.${id}`) ``, `` t(`order.financial.${status}`) ``,
  `` t(`preferences.tone.${tone}`) ``. TypeScript checks that such keys exist.
- **Logic in `app/lib` returns codes, not sentences.** Recommendation reasons are
  `{code, value?}` (`app/lib/recommendation/types.ts`); the UI translates
  `recommendation.reason.<code>`. Preference labels come from the dictionaries, not from
  `preferences.ts`.
- Placeholders use `{name}` and are filled from the values object. Unknown placeholders are
  left as they are.
- **Plurals**: a message that depends on a number is an object of `Intl.PluralRules`
  categories with `other` required, e.g.
  `{one: 'Open cart with {count} item', other: 'Open cart with {count} items'}`. Call
  `t('nav.openCart', {count})`; `createTranslator` picks the form with
  `Intl.PluralRules(<locale tag>)`. pt-PT uses `one` for 1 and `other` for 0, 2, 21…;
  fr-FR uses `one` for 0 and 1, `many` for large round numbers (1 000 000) and `other`
  otherwise. Without a numeric `count` it uses `other`. Never choose singular/plural in
  components.
- Sentences around a value use one message with a placeholder, never concatenated
  fragments. Values that are React elements are avoided: a search term is quoted inside the
  message with the language's own quotation marks.

### Adding a language

The supported languages are EN, PT and FR (US-046). Shopify accepting a `LanguageCode`
does not make a language supported. Enable another language (e.g. German) only when all of
these hold:

1. **UI messages**: a complete `app/lib/messages/<code>.ts` typed as `Messages`, added to
   `MESSAGES` in `app/lib/i18n.ts`; typecheck enforces every key.
2. **Shopify**: the language is added and published for the market(s) the storefront uses,
   and its content is translated.
3. **Verified mapping**: the app code, BCP 47 tag and Shopify `LanguageCode` are checked
   against the installed schema and against `localization.availableLanguages` from the
   store (as done for `PT_PT` and `FR` above).

Then add one entry to `LOCALES` (e.g. `de: {language: 'DE', tag: 'de-DE', name:
'Deutsch', short: 'DE', flag: 'de'}`, adding the flag to `FlagKey` and
`LanguageSelector.tsx`). Cookie validation, `POST /locale`, Accept-Language negotiation,
the selector and `<html lang>` all read `LOCALES`, so no detection code changes. Re-measure
the desktop header: each option adds 44px (see
[responsive.md → Site header modes](responsive.md#site-header-modes)).

### Adding a string

1. Add the key and English text to `app/lib/messages/en.ts`, in the section of its module
   (prefix such as `cart.` or `product.`).
2. Add the pt-PT text to `pt.ts` and the French text to `fr.ts`, following the
   [glossary](#glossary). `npm run typecheck` fails until every language has the key.
3. Use it with `t('your.key')` in components, `translatorFor(...)` in loaders/actions, or
   `translatorFromMatches(matches)` in `meta`.
4. Do not concatenate translated fragments; use one message with placeholders. Counts use a
   plural message.
5. Run `npm test`: `messages.test.ts` checks completeness, placeholders, unused keys and
   French spacing.
6. Run `npm run lint`: it fails on literal text in JSX and on literal `aria-label`,
   `title`, `alt` or `placeholder` values, so a string that skipped the dictionaries is caught.
   Symbols without letters (`→`, `·`, `×`, `©`…) are allowed in `eslint.config.js`.

## How the language reaches Shopify

- Storefront documents declare `$language`/`$country` and use
  `@inContext(language: $language, country: $country)`.
- Hydrogen's storefront client fills `$language`/`$country` from `context.storefront.i18n`
  when the caller does **not** pass them (verified in the Hydrogen dist code). **Do not pass
  `language` explicitly.**
- No loader passes a language: the 8 hardcoded `language: 'EN'` values (home, collections,
  product, product cards by id, recommendation candidates) were removed in US-046.
- `tests/unit/locale-propagation.test.ts` checks this. It fails if a literal
  `language: '…'` comes back in `app/`; if a GraphQL operation in `app/` lacks
  `$language: LanguageCode` and `@inContext(language: $language)` (the customer metafield
  documents, which hold only IDs and JSON, are allowlisted); or, using Hydrogen's real
  storefront client and `InMemoryCache`, if a PT or FR request gets a cached English
  response or the country changes with the language.
- Header and footer menus (`Header`/`Footer` queries in `root.tsx`) and every other
  Storefront query therefore use the active language. Menu titles are translated in the
  admin (Navigation), like other content. In PT and FR Shopify returns menu URLs with a
  language folder (`/pt/collections/…`); the app has no such routes (the language comes
  from the cookie), so `toMenuPath()` in `app/lib/menu.ts` drops the folder for the header
  and footer links.
- Customer Account documents use `@inContext(language: $language)`, and the account routes
  pass `customerAccount.i18n.language`.
- Customer Account login: Hydrogen sends the context language as the `locale` parameter
  (`PT_PT` → `pt-PT`, `FR` → `fr`) unless `?locale=` overrides it (`account_.login.tsx`). This was checked
  in the Hydrogen source, not end to end.

## Formatting

- **Money**: Hydrogen's `<Money>` takes its locale from a `<ShopifyProvider>`, which this app
  does not render, so it always formatted as en-US (checked in the Hydrogen source).
  `app/components/shared/Money.tsx` replaces it everywhere and uses `formatMoney()` with the
  active tag: `€1,234.50` / `1234,50 €` / `1 234,50 €`. Only separators and symbol position
  change; the currency and amount always come from the API (EUR today).
- **Dates**: `formatDate()` with the active tag (orders, order detail, blog posts):
  "November 12, 2026" / "12 de novembro de 2026" / "12 novembre 2026".
- **Lists**: `formatList()` (`Intl.ListFormat`), e.g. the allergens in the allergy warning.
- **Plurals**: plural messages, see [UI messages](#ui-messages).

## Shopify administration setup

Catalog content is translated in Shopify, not in this repository. **None of these steps
needs a frontend commit**: every Storefront query already sends the active language (see
[How the language reaches Shopify](#how-the-language-reaches-shopify)), so content appears
in Portuguese or French as soon as Shopify returns it. Changing Shopify settings or content
needs separate approval; nothing below has been done.

**Current state** (read-only Storefront API checks, 2026-11-11, with the token in `.env`):

- `localization.availableLanguages` lists only `EN`. A request with
  `@inContext(language: PT_PT)` or `FR` is answered with `extensions.context.language: EN`, so
  every menu, product, collection and blog title is English. This is the cause of the
  English content seen after choosing PT or FR; it is not a locale-propagation defect.
- `localization.availableCountries` lists only `PT`. Every `@inContext(country:)` value
  tried (`US`, `PT`, `FR`, `ES`, `GB`, `BR`) resolves to country `PT`, market handle `pt`,
  currency EUR. So the app's default country `US` currently resolves to the **Portugal
  market**, and the languages must be added to that market.
- An earlier read-only Admin check (same day) found `en` as the only published and primary
  locale, with four market web presences that have no alternate locales.

### Steps in the Shopify admin

Labels follow the current Shopify admin and may differ slightly. Keep English as the
primary (default) language throughout.

1. **Add the languages.** Settings → Languages → *Add language* → **Portuguese
   (Portugal)**, then again for **French**. Each new language starts unpublished.
2. **Publish them.** Settings → Languages → each language → *Publish*. Unpublished
   languages are not returned by the Storefront API.
3. **Make them available in the Portugal market.** Settings → Markets → **Portugal**
   (handle `pt`; it is the only market this storefront resolves to, see above) → languages
   (*Domains and languages*) → add Portuguese (Portugal) and French. Keep English as the
   market's default. If other markets are later opened to this storefront, add the
   languages there too.
4. **Translate with Translate & Adapt** (Shopify's free app; install it from the Shopify App
   Store if missing). Apps → Translate & Adapt → choose the language at the top, then
   translate each resource type below. The app's machine translation is optional; have
   native speakers review the result.

| What the shopper sees | Translate & Adapt resource | Notes |
| --- | --- | --- |
| Header menu ("Trending", "Watches", …) | Navigation → `main-menu` | Menu item titles. Menus are cached for up to 1 h by the app (`CacheLong`); see verification. |
| Footer links ("Search", "Privacy Policy") | Navigation → `footer` | |
| Home sections | Navigation → `home-content` | **Do not translate the item titles "Hero", "Featured", "Story"**: the home loader finds those items by title (`findCollection` in `app/routes/_index.tsx`). Translating them would hide those home sections. |
| Product titles, descriptions, option names and values ("Color", "Gold") | Products | Also the SEO title and meta description on the same screen (used for page titles and descriptions). |
| Collection titles and descriptions ("Bracelets", "Customizable") | Collections | Also SEO title and description. |
| Blog name ("News"), article titles, bodies and excerpts | Blogs / Blog posts | |
| Pages | Pages | Also SEO fields. |
| Policies ("Refund Policy", "Privacy Policy") | Policies | |
| Product badge ("New In", "Limited Edition"), metal, gemstone, gem colour | Metafields (product) | Values of `custom.product_badge`, `custom.metal`, `custom.gemstone`, `custom.gem_color`. Only text-type metafield values are translatable; whether a value limited to preset choices can be translated was **not verified**. |
| Material labels ("Stainless steel", "Faux leather") | Metaobjects | The material metaobject definition must allow translations (Settings → Custom data → Metaobjects → the definition → *Translations* capability, where shown). **Not verified** for this store. |
| Filter values ("Gold", "Silver") and names of filters the app does not name | Filters (Search & Discovery) | The app names availability, price, product type, brand, material, metal and gem colour itself, so translating those seven names in Shopify has no visible effect. Filter **values** come from the translated product and metafield data. |

5. **Leave one product without a Portuguese description** (translate its title only), to
   check the English fallback.
6. **Checkout and customer accounts** are Shopify-hosted. The app sends the active language
   to Customer Account login (`locale`, e.g. `pt-PT`, `fr`) and to the cart; the checkout
   language for a cart created in PT/FR was **not tested**.

### Read-only verification

After saving and publishing, without changing anything:

1. Storefront API (GraphiQL at `/graphiql` on the dev server, or any client with the
   public Storefront token), for each language:
   ```graphql
   query @inContext(language: PT_PT) {
     localization {
       language { isoCode }
       availableLanguages { isoCode }
       country { isoCode market { handle } availableLanguages { isoCode } }
     }
     menu(handle: "main-menu") { items { title } }
     products(first: 3) { nodes { title } }
   }
   ```
   Expected: `language.isoCode` is `PT_PT` (then `FR` with `@inContext(language: FR)`);
   `availableLanguages` lists `EN`, `PT_PT` and `FR`; `extensions.context.language` in the
   response equals the requested code; the titles are translated. If Portuguese is listed
   as `PT` instead of `PT_PT`, change `LOCALES.pt.language` in `app/lib/i18n.ts` (the only
   code change that could be needed).
2. Restart the local server, or on Oxygen allow up to an hour: header and footer menus are
   cached with `CacheLong` (1 h fresh, then refreshed in the background); other queries
   refresh within seconds.
3. Open the store in a fresh browser set to Portuguese (or choose PT): menus, product and
   collection titles are in Portuguese, and `<html lang="pt-PT">`.
4. Open the product left without a Portuguese description: the English description is shown
   with no error. (The app side is covered with mocked responses in
   `tests/unit/translation-fallback.test.ts`; this step checks the real store.)
5. Repeat 3–4 for French.
6. Run the staging checks in [Caching → Staging verification](#staging-verification-still-to-do-after-deployment).
